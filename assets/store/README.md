## Member screenshot templates

Each device has three templates under `templates/`: equipment catalogue,
borrowing request form, and My Borrow Requests. They contain capture slots,
not fabricated member interfaces. After signing in, capture the actual native
screens without exposing private member information, and save them as:

- `captures/ios/04-kit-catalogue.png`, `05-kit-request.png`, `06-my-requests.png`
- `captures/ipad/04-kit-catalogue.png`, `05-kit-request.png`, `06-my-requests.png`
- `captures/android/04-kit-catalogue.png`, `05-kit-request.png`, `06-my-requests.png`

Keep the capture at the same device dimensions shown in the table. Run:

```bash
python3 scripts/store-assets/generate.py
```

The generator fills each layout using its real capture, moves the result into
the finished screenshot folder, removes its placeholder template, and refreshes
`preview.html` and `manifest.json`. It rejects captures of the wrong device size
rather than stretching the UI. Once filled, upload in this order: catalogue,
request form, request history, UCL sign-in, home, join invitation. Google
recommends at least four screenshots for promotional recommendation formats;
three public screenshots are ready now, with the member captures still needed
for the complete six-image set.

The source icon is `branding/app_icons/app-icon.svg`. Run
`scripts/generate-app-icons.sh` and then the store generator when it changes.
The feature graphic is regenerated by the store script from the vector layout
in `scripts/store-assets/generate.py`; its rendered SVG is included here.
Dependencies: Python 3, `rsvg-convert`, and ImageMagick (`magick`).

## Tester and reviewer setup

Installation access and app sign-in are separate. Invite iPhone testers in App
Store Connect → TestFlight. For people outside your App Store Connect team,
create an External Testing group, add an uploaded build, submit the first build
for TestFlight review, then invite by email or public link. Testers install the
TestFlight app using their Apple Account. On Android, use Play Console → Test
and release → Testing → Internal testing (or Closed testing), add a list of
testers' Google Account emails, upload the AAB, and send the opt-in link.

Testers with UCL accounts and active Hiking Club membership can use normal UCL
sign-in after installation. Their Apple/Google tester account is only for
installing the build; it is not an app login.

Store reviewers sign in with the Toolbox reviewer accounts
(`apple@` / `android@adamscampustoolbox.org.uk`), not UCL. On the app's sign-in
page, seven taps on the “UCL Hiking Club × Adam's Campus Toolbox” line reveal an
email/password form (`/api/auth/review`, which signs in through Toolbox's
`/api/auth/backdoor`). Put the email and password in App Store Connect's App
Review Information and Play Console's App content → App access, never in this
repository. See `copy/reviewer-notes.md` for the exact steps to paste.

The native shells are configured to load `https://ucl-hiking.vercel.app`.
Run `npm run cap:sync` before each native build if the deployment URL changes.
Capture screenshots only after testing sign-in on each native platform.
Allow `https://ucl-hiking.vercel.app` as a bare origin in the Toolbox Hiking
organiser's site settings. Browser sign-in returns to the domain on which it
started, so there is no single production `NEXT_PUBLIC_APP_URL` setting to
change when another domain is added.

The store privacy questionnaires must be completed from the deployed build and
its service providers. At minimum, assess name/email/club membership, bookings,
equipment requests, authentication/session data, and server logs. Do not claim
the app collects no data.

## When uclhiking.org moves to this app

There is no DNS change to make now; `uclhiking.org` currently serves the older
club site. At the switch:

1. Add `uclhiking.org` (and `www.uclhiking.org` if it will be used) to the
   **ucl-hiking** Vercel project's Domains settings, then use Vercel's displayed
   DNS records rather than copying a generic record. Preserve MX, SPF, DKIM and
   other email records so `privacy@uclhiking.org` keeps receiving mail.
2. Register each new HTTPS bare origin in the Toolbox Hiking organiser's
   allowed-site list. Browser sign-in uses the origin that started the request;
   test sign-in and `/auth/callback` on the apex and `www` addresses that will
   actually serve the app.
3. Check `https://uclhiking.org/privacy` and the account-deletion link after
   HTTPS is ready. Update the store policy URL if you want the custom domain
   shown in Apple and Google. The current Vercel privacy URL can stay in the
   store as long as it continues to serve this app and policy.
4. Keep `ucl-hiking.vercel.app` working while native builds still load it. If
   you later redirect that address or want native builds to use the new domain,
   change `CAPACITOR_APP_URL`, sync, test sign-in, and ship updated native builds.

Session cookies are scoped to the host that set them. A user who switches
between the Vercel and custom web addresses may need to sign in again until one
address is chosen as the primary web address.
